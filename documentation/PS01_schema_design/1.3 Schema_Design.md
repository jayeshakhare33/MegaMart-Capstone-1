# MegaMart Database Schema Design Rationale

## 1. Purpose
This schema supports a supermarket retail dataset for managing:
- stores
- products
- suppliers
- sales transactions
- inventory
- purchase orders

The design is intended to be simple, normalized, and suitable for reporting and operational analysis.

## 2. Design Principles
The schema follows:
- Normalization: each entity is stored once in a master table
- Referential integrity: relationships are enforced through foreign keys
- Clear separation: master data and transactional data are stored separately
- Business readability: table names and columns match retail operations

## 3. Table Design Decisions

### 3.1 stores
```sql
CREATE TABLE stores (
    store_id INT NOT NULL,
    store_name VARCHAR(100),
    location VARCHAR(100),
    manager_name VARCHAR(100),
    PRIMARY KEY (store_id)
);
```

Reason:
- `store_id` uniquely identifies each store.
- Store details are kept in one place instead of duplicating them across sales records.
- This supports store-level reporting and operations.

### 3.2 products
```sql
CREATE TABLE products (
    product_id INT NOT NULL,
    product_name VARCHAR(150),
    category VARCHAR(100),
    unit_price DECIMAL(10,2),
    PRIMARY KEY (product_id)
);
```

Reason:
- `product_id` uniquely identifies each product.
- Product attributes are stored once rather than repeated in every transaction.
- `unit_price` uses `DECIMAL(10,2)` to preserve money accurately.

### 3.3 suppliers
```sql
CREATE TABLE suppliers (
    supplier_id INT NOT NULL,
    supplier_name VARCHAR(150),
    contact_person VARCHAR(100),
    phone VARCHAR(20),
    PRIMARY KEY (supplier_id)
);
```

Reason:
- Supplier data is a separate master entity.
- This avoids duplication and keeps procurement data organized.

### 3.4 sales_transactions
```sql
CREATE TABLE sales_transactions (
    transaction_id INT NOT NULL,
    store_id INT,
    product_id INT,
    quantity_sold INT,
    sale_date DATE,
    PRIMARY KEY (transaction_id),
    FOREIGN KEY (store_id) REFERENCES stores(store_id),
    FOREIGN KEY (product_id) REFERENCES products(product_id)
);
```

Reason:
- Sales are transactional facts linked to both the store and the product.
- `quantity_sold` and `sale_date` allow sales trend and performance analysis.
- The sales table remains focused on transaction-level facts.

### 3.5 inventory
```sql
CREATE TABLE inventory (
    inventory_id INT NOT NULL,
    store_id INT,
    product_id INT,
    quantity_on_hand INT,
    PRIMARY KEY (inventory_id),
    FOREIGN KEY (store_id) REFERENCES stores(store_id),
    FOREIGN KEY (product_id) REFERENCES products(product_id)
);
```

Reason:
- Inventory reflects stock availability by store and product.
- This enables stock monitoring, replenishment decisions, and product availability analysis.

### 3.6 purchase_orders
```sql
CREATE TABLE purchase_orders (
    po_id INT NOT NULL,
    supplier_id INT,
    order_date DATE,
    delivery_date DATE,
    PRIMARY KEY (po_id),
    FOREIGN KEY (supplier_id) REFERENCES suppliers(supplier_id)
);
```

Reason:
- Purchase orders represent procurement activity.
- `order_date` and `delivery_date` support analysis of order timing and supplier performance.

## 4. Referential Integrity
The schema enforces valid relationships:
- Sales must belong to a valid store and product
- Inventory must belong to a valid store and product
- Purchase orders must belong to a valid supplier

This protects the database from inconsistent or broken data.

## 5. Importance of Normalization
The design avoids duplication by storing data in master tables and linking them with keys. For example:
- store data is stored once in `stores`
- product data is stored once in `products`
- supplier data is stored once in `suppliers`

This keeps the data consistent and easier to maintain.

## 6. Gold Layer Design (Views)

The gold layer uses **9 views + 1 table** (replacing 18 physical tables).
All views are defined in `gold_layer_views.sql` and query the Silver layer
directly — no storage, no stale data, no manual table updates.

### Why views instead of tables?
- **No stale data**: views always reflect the latest Silver state.
- **No storage cost**: views are just stored SQL definitions.
- **No maintenance**: no need to re-run gold stages after Silver updates.
- **Simpler pipeline**: the gold build stages are replaced by a single SQL file.

### View inventory

| Object | Type | Rows | Replaces former tables |
|--------|------|------|-----------------------|
| `store_performance` | View | 5 | store_sales_summary, store_revenue_ranking, store_product_diversity, store_kpi_summary, dashboard_store_performance |
| `product_performance` | View | 70 | product_store_sales, product_velocity |
| `top_products` | View | 5 | top_products |
| `monthly_store_trends` | View | 60 | monthly_store_sales |
| `monthly_kpis` | View | 12 | monthly_kpi_summary, dashboard_monthly_trend |
| `category_kpis` | View | 7 | category_kpi_summary, dashboard_category_performance |
| `enterprise_kpi` | View | 1 | enterprise_kpi_summary, dashboard_enterprise_summary |
| `inventory_status` | View | 70 | inventory_status |
| `supplier_scorecard` | View | 12 | supplier_scorecard |
| `reorder_recommendations` | **Table** | 70 | (unchanged — complex Python logic) |

### Design decisions

- **`reorder_recommendations` stays as a table** because it involves
  multi-step Python logic (daily demand calculation, safety stock,
  reorder points, lead-time lookups) that benefits from materialization.
- **Runtime columns dropped**: `_kpi_run_id`, `_kpi_processed_at`,
  `_dashboard_run_id`, `_dashboard_processed_at` are not included in views
  because they would be misleading (a view's `current_timestamp()` evaluates
  at query time, not at computation time). Run tracking is handled by
  `audit.pipeline_runs`.
- **Consolidation rationale**: 5 store-level tables → 1 view, 2
  store×product tables → 1 view, 2 monthly tables → 1 view, 2 category
  tables → 1 view, 2 enterprise tables → 1 view. The former tables had
  significant duplication (e.g., store_sales_summary and store_kpi_summary
  both aggregated sales by store with the same metrics).

## 7. Conclusion
This schema is a practical relational model for a supermarket system. It separates master data from transactional data, maintains data integrity through foreign keys, and supports key retail analyses such as sales performance, stock monitoring, and supplier management.
