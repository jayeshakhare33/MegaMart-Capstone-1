# MegaMart Database Schema Design Rationale

## 1. Purpose
This schema supports a supermarket retail dataset for managing:
- stores
- products
- suppliers
- sales transactions
- inventory
- purchase orders

The design is intended to be simple, normalized, and suitable for reporting and operational analysis.

## 2. Design Principles
The schema follows:
- Normalization: each entity is stored once in a master table
- Referential integrity: relationships are enforced through foreign keys
- Clear separation: master data and transactional data are stored separately
- Business readability: table names and columns match retail operations

## 3. Table Design Decisions

### 3.1 stores
```sql
CREATE TABLE stores (
    store_id INT NOT NULL,
    store_name VARCHAR(100),
    location VARCHAR(100),
    manager_name VARCHAR(100),
    PRIMARY KEY (store_id)
);
```

Reason:
- `store_id` uniquely identifies each store.
- Store details are kept in one place instead of duplicating them across sales records.
- This supports store-level reporting and operations.

### 3.2 products
```sql
CREATE TABLE products (
    product_id INT NOT NULL,
    product_name VARCHAR(150),
    category VARCHAR(100),
    unit_price DECIMAL(10,2),
    PRIMARY KEY (product_id)
);
```

Reason:
- `product_id` uniquely identifies each product.
- Product attributes are stored once rather than repeated in every transaction.
- `unit_price` uses `DECIMAL(10,2)` to preserve money accurately.

### 3.3 suppliers
```sql
CREATE TABLE suppliers (
    supplier_id INT NOT NULL,
    supplier_name VARCHAR(150),
    contact_person VARCHAR(100),
    phone VARCHAR(20),
    PRIMARY KEY (supplier_id)
);
```

Reason:
- Supplier data is a separate master entity.
- This avoids duplication and keeps procurement data organized.

### 3.4 sales_transactions
```sql
CREATE TABLE sales_transactions (
    transaction_id INT NOT NULL,
    store_id INT,
    product_id INT,
    quantity_sold INT,
    sale_date DATE,
    PRIMARY KEY (transaction_id),
    FOREIGN KEY (store_id) REFERENCES stores(store_id),
    FOREIGN KEY (product_id) REFERENCES products(product_id)
);
```

Reason:
- Sales are transactional facts linked to both the store and the product.
- `quantity_sold` and `sale_date` allow sales trend and performance analysis.
- The sales table remains focused on transaction-level facts.

### 3.5 inventory
```sql
CREATE TABLE inventory (
    inventory_id INT NOT NULL,
    store_id INT,
    product_id INT,
    quantity_on_hand INT,
    PRIMARY KEY (inventory_id),
    FOREIGN KEY (store_id) REFERENCES stores(store_id),
    FOREIGN KEY (product_id) REFERENCES products(product_id)
);
```

Reason:
- Inventory reflects stock availability by store and product.
- This enables stock monitoring, replenishment decisions, and product availability analysis.

### 3.6 purchase_orders
```sql
CREATE TABLE purchase_orders (
    po_id INT NOT NULL,
    supplier_id INT,
    order_date DATE,
    delivery_date DATE,
    PRIMARY KEY (po_id),
    FOREIGN KEY (supplier_id) REFERENCES suppliers(supplier_id)
);
```

Reason:
- Purchase orders represent procurement activity.
- `order_date` and `delivery_date` support analysis of order timing and supplier performance.

## 4. Referential Integrity
The schema enforces valid relationships:
- Sales must belong to a valid store and product
- Inventory must belong to a valid store and product
- Purchase orders must belong to a valid supplier

This protects the database from inconsistent or broken data.

## 5. Importance of Normalization
The design avoids duplication by storing data in master tables and linking them with keys. For example:
- store data is stored once in `stores`
- product data is stored once in `products`
- supplier data is stored once in `suppliers`

This keeps the data consistent and easier to maintain.

## 6. Gold Layer Design (Views)

The gold layer uses **10 views + 1 table** (replacing 18 physical tables).
All views are defined in `gold_layer_views.sql` and query the Silver layer
directly — no storage, no stale data, no manual table updates.

### Why views instead of tables?
- **No stale data**: views always reflect the latest Silver state.
- **No storage cost**: views are just stored SQL definitions.
- **No maintenance**: no need to re-run gold stages after Silver updates.
- **Simpler pipeline**: the gold build stages are replaced by a single SQL file.

| `top_products` | View | 5 | top_products |
| `monthly_store_trends` | View | 60 | monthly_store_sales |
| `monthly_kpis` | View | 12 | monthly_kpi_summary, dashboard_monthly_trend |

### View Definitions & Query Logic

#### 1. store_performance
- **Granularity**: One row per store (5 rows)
- **Purpose**: Store-level sales, rankings, diversity, KPIs, and inventory health
- **Key Metrics**:
  - transaction_count, total_quantity_sold, total_revenue
  - average_transaction_value, unique_products_sold
  - unique_categories_sold
  - revenue_rank, transaction_count_rank
  - store_revenue_share_pct (% of chain total)
  - inventory_turnover_ratio (units-based approximation)
  - market_share_pct (internal chain share)
  - Inventory health metrics: current_inventory_units, out_of_stock_skus, low_stock_skus, healthy_stock_skus
  - inventory_health_pct (% of catalog with healthy stock)

#### 2. product_performance
- **Granularity**: One row per store×product (70 rows)
- **Purpose**: Store×product sales, velocity, rankings, and stock status
- **Key Metrics**:
  - Sales metrics: total_quantity_sold, transaction_count, total_revenue, average_selling_price
  - store_revenue_share_pct (% of store revenue)
  - Ranks: revenue_rank_within_store, quantity_rank_within_store, overall_velocity_rank, store_velocity_rank
  - Velocity metrics: average_daily_sales, estimated_days_of_inventory
  - velocity_class: NO_SALES, SLOW_MOVING, NORMAL_MOVING, FAST_MOVING
  - stock_status: OUT_OF_STOCK, LOW_STOCK, HEALTHY
  - profitability_status: placeholder (no unit cost available)

#### 3. top_products
- **Granularity**: Top 5 products by quantity sold (5 rows)
- **Purpose**: Quick view of best-selling products chain-wide
- **Key Metrics**:
  - quantity_rank, product details (id, name, category)
  - total_quantity_sold, total_revenue, transaction_count

#### 4. monthly_store_trends
- **Granularity**: One row per store×month (5 stores × 12 months = 60 rows)
- **Purpose**: Per-store monthly sales with Month-over-Month (MoM) metrics
- **Key Metrics**:
  - monthly_quantity_sold, monthly_revenue, monthly_transaction_count
  - mom_revenue_change (absolute $), mom_revenue_growth_pct (%)
  - Complete Jan–Dec 2024 grid (even months with zero sales)

#### 5. monthly_kpis
- **Granularity**: One row per month (12 rows, chain-wide)
- **Purpose**: Chain-wide monthly KPIs with MoM change percentages
- **Key Metrics**:
  - total_revenue, transaction_count, avg_transaction_value
  - unique_products_sold, units_sold, categories_sold
  - mom_revenue_change_pct, mom_transaction_change_pct, mom_units_change_pct
  - month_label (human-readable format, e.g., "Jan 2024")

#### 6. category_kpis
- **Granularity**: One row per category (7 rows)
- **Purpose**: Category-level performance with ranking and revenue share
- **Key Metrics**:
  - total_revenue, units_sold, transaction_count, unique_products_sold
  - avg_transaction_value, category_rank
  - top_3_category_flag (boolean)
  - revenue_share_pct (% of chain revenue)

#### 7. enterprise_kpi
- **Granularity**: Single row (chain-wide summary)
- **Purpose**: Complete chain-wide business summary
- **Key Metrics**:
  - project_start_date, project_end_date
  - total_revenue, transaction_count, avg_transaction_value
  - unique_products_sold, total_products_in_catalog
  - active_stores, total_stores_in_master
  - current_inventory_units, units_sold
  - inventory_turnover_ratio (units-based approximation)
  - market_share_pct (100%, internal chain share)
  - internal_store_revenue_share_available (true)
  - out_of_stock_skus, low_stock_skus
  - avg_monthly_revenue, dashboard_period

#### 8. inventory_status
- **Granularity**: One row per store×product (70 rows)
- **Purpose**: Simple stock-status classification
- **Key Metrics**:
  - inventory_id, store details, product details, supplier details
  - quantity_on_hand
  - stock_status: OUT_OF_STOCK, LOW_STOCK, HEALTHY
  - stock_priority: numeric 1–3 (1=healthy, 2=low, 3=out-of-stock)

#### 9. supplier_scorecard
- **Granularity**: One row per supplier (12 rows)
- **Purpose**: Supplier delivery performance tracking
- **Key Metrics**:
  - total_purchase_orders, delivered_orders
  - failed_or_incomplete_orders
  - delivery_reliability_pct (% delivered on time)
  - average_lead_time_days, minimum_lead_time_days, maximum_lead_time_days
  - reliability_definition (for audit/clarity)

#### 10. store_category_top3
- **Granularity**: Up to 3 rows per store (15 rows max for 5 stores)
- **Purpose**: Top 3 categories by revenue for each store (used in Comparative Store Performance Dashboard)
- **Key Metrics**:
  - store_id, store_name, category
  - category_revenue (rounded to 2 decimals), units_sold, transaction_count
  - cat_rank (1, 2, or 3)

### Design Decisions

- **`reorder_recommendations` stays as a table** because it involves
  multi-step Python logic (daily demand calculation, safety stock,
  reorder points, lead-time lookups) that benefits from materialization.
- **Runtime columns dropped**: `_kpi_run_id`, `_kpi_processed_at`,
  `_dashboard_run_id`, `_dashboard_processed_at` are not included in views
  because they would be misleading (a view's `current_timestamp()` evaluates
  at query time, not at computation time). Run tracking is handled by
  `audit.pipeline_runs`.
- **Consolidation rationale**: 5 store-level tables → 1 view, 2
  store×product tables → 1 view, 2 monthly tables → 1 view, 2 category
  tables → 1 view, 2 enterprise tables → 1 view. The former tables had
  significant duplication (e.g., store_sales_summary and store_kpi_summary
  both aggregated sales by store with the same metrics).
- **`store_category_top3` added** to support the Comparative Store Performance
  Dashboard (Problem 5) — provides top categories per store at a glance.

## 7. Query Computation Strategy

All views use the following patterns for reliability:

1. **NULLIF guards**: Prevent division by zero errors in ratios.
2. **COALESCE for zero-filling**: Months/stores with no sales return 0, not NULL.
3. **Window functions**: DENSE_RANK, ROW_NUMBER, LAG for rankings and MoM calculations.
4. **Standard rounding**: Decimals rounded to 2 places for currency, 4 places for derived metrics.
5. **Hard-coded ranges**: 2024-01-01 to 2024-12-31 (from project scope).

## 8. Conclusion
This schema is a practical relational model for a supermarket system. It separates master data from transactional data, maintains data integrity through foreign keys, and supports key retail analyses such as sales performance, stock monitoring, and supplier management. The gold layer's 10 views replace 18 former tables, eliminating redundancy and ensuring data is always current—views compute on-demand from the Silver layer, guaranteeing consistency and reducing maintenance overhead.
